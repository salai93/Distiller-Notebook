## Teamcenter publication error on physical link "Buttons/Knobs"

**Source:** a Capella/SMW Eclipse log (.log) the user uploaded, covering 2026-11-10 to 11-15. The same error appears on every Distiller Project publication from 2026-11-12 11:48 through 2026-11-15 20:42. Model checked against Distiller-Project @ master.

### The error
"Given GeneralDesignElement when expecting ItemRevision" / "System could not find 256563fd-d6b7-4f64-ad08-253699cd565d provided for an attribute owningComponentIdentifier" / "Error while processing connection cs.PhysicalLink_b90e1bc7… between cs.PhysicalPort_7e77eb2b… and cs.PhysicalPort_01af1def…"

### What the IDs are in the model
- b90e1bc7 = PA physical link **Buttons/Knobs**, owned by the root **Structure** package
- 7e77eb2b = PP 3 on the **Operator** actor, which sits under Structure, outside the system
- 01af1def = PP 1 on the **Control Panel**, which sits under Physical System → Water Distiller
- 256563fd = the **Physical System Part**: the usage of the root component, not the component itself

### Diagnosis
The link is owned at Structure level and runs across the system boundary, so the publisher gives it the root Physical System Part as its owning component. Teamcenter holds that Part as a GeneralDesignElement, but a connection's owner must be a component ItemRevision. Teamcenter therefore can't resolve the owner and rejects the connection.

Buttons/Knobs is also the only PA physical link that **carries no component exchange**. Every other boundary link, such as SourcePipeline, Heat and CleanWaterDistributionPipeline, is also owned by Structure but carries one. This is the most likely reason only this link fails. Not confirmed: the Teamcenter server syslog would show it.

### Pattern in the log
The same "GeneralDesignElement vs ItemRevision" error hit several component exchanges on 2026-11-11: 0356d8ca and 57855524, both no longer in the model, and 07b5c72b. It also hit a "Structure ↔ WaterSupplyControl" relation. Each failure is a connection or relation owned at the top Structure level.

### Side finding
Component exchange **07b5c72b "HeatSupply"** still exists, under Structure with no layer. The live HeatSupply in PA is b777d0e4. This looks like a leftover duplicate that could trip a future publish.

### Candidate fixes (not applied)
1. Allocate a component exchange to Buttons/Knobs (Operator ↔ User Interface operator commands), matching the other boundary links.
2. Or move the link's ownership so its owner resolves to a component.
3. Check in Teamcenter that the Physical System root was published as an Item/ItemRevision.
4. Remove the stray HeatSupply 07b5c72b.

## Update 2026-11-15 22:52: after the user's fix (commit b22cc6d8, "second commit")

The user added component exchange **Operation** (b82f8439) and allocated it to Buttons/Knobs. Operation runs from Operator CP 4 (b4cc3078) to User Interface CP 2 (4ac2c294), is owned by Structure, and carries the Startup and Shutdown functional exchanges.

**Result:** the physical-link error is gone. Publication now fails on Operation instead, with the same "Given GeneralDesignElement when expecting ItemRevision" error.

**Comparison with Pipeline (7bac67af), which publishes fine:**
- Both are owned by Structure.
- Both run from an actor node to a behavior component under Physical System.
- Both are allocated to a physical link.

The only differences are that Operation carries no exchange item and that it carries control flows rather than material. Neither should affect how Teamcenter resolves an owner. The PA model check is clean.

**Revised hypothesis:** the cause is now more likely on the Teamcenter side than in the model. Operator is the one actor none of whose connections has ever published; Buttons/Knobs failed on every attempt since 2026-11-12. The Operator, or what remains of an earlier failed publication, probably sits in Teamcenter as a GeneralDesignElement rather than an ItemRevision. On 2026-11-11 the same error cleared once HeatSupply was recreated, and the older copy, 07b5c72b, is still a stray in the model. The Teamcenter syslog or an admin check of the Operator object would confirm.

## Correction 2026-11-15 23:13: HeatSupply 07b5c72b is NOT a stray

Earlier versions of this entry called component exchange 07b5c72b "HeatSupply" a leftover duplicate and recommended deleting it. **That was wrong. Do not delete it.**

07b5c72b is the **Logical Architecture** HeatSupply. It runs from the LA Heat Source (911497c8) to the LA Evaporator (b4f375a8) and carries the LA Heat3 exchange, with exchange item externalHeat. b777d0e4 is its **Physical Architecture** counterpart, between the PA Heat Source and the PA Evaporator. Having both is normal Capella layering. The mistake came from the lookup tool showing both with no layer and parent "Structure". In fact each one sits under its own layer's Structure package.

The 2026-11-11 publish error on 07b5c72b was therefore an LA-level exchange hitting the same GeneralDesignElement/ItemRevision problem, not a sign of an orphan element.
